# 02 — The résumé as a product

**Status:** v1.0, 2026-10-24. Implements `docs/DESIGN.md` §7. Phase 1 for RES-01 – RES-12; Phase 2 for RES-20; Phase 3 for RES-30.

## Purpose

One file, `src/data/resume.json`, is the only place the résumé is edited. The build renders it as the web page `/resume/`, the download `/resume.pdf`, the machine-readable `/resume.json`, and the `schema.org/Person` JSON-LD used on the home and About pages. The `.docx` Michael maintains today is retired when the PDF matches it.

## Requirements

### Source of truth

**RES-01** `src/data/resume.json` MUST validate against `src/lib/resume.schema.ts`, a Zod schema that is a superset of [JSON Resume v1.0.0](https://jsonresume.org/schema). The superset adds exactly two things, both optional:

- `work[].highlights[]` entries MAY be an object `{ "text": string, "lenses"?: ("leadership"|"architecture"|"consulting")[], "evidence"?: string }` instead of a plain string. `evidence` is a site-relative URL (`/posts/native-aot-lambda/`) or absolute URL.
- A top-level `meta.lenses` object mapping lens id to display name and one-line description.

Everything else (`basics`, `work`, `skills`, `education`, `projects`, `languages`, …) keeps JSON Resume's shape and field names.

**RES-02** The schema MUST reject: a `work[]` entry whose `endDate` precedes `startDate`; two `work[]` entries with overlapping dates unless one carries `"meta": { "overlap": true }`; a `highlights[].evidence` that is site-relative and does not resolve to a built page (checked post-build, see RES-11).

**RES-03** `skills[]` MUST NOT carry years or levels typed by hand. Years per skill and total years of experience are computed at build from `work[]` dates (RES-07).

**RES-04** The phone number MUST NOT appear in `resume.json`, on any page, or in the PDF. Email and profile links are the public contact surface.

### Outputs

**RES-05** `/resume.json` MUST be strict JSON Resume: the same data with every highlight object flattened to its `text` and the `meta.lenses` key removed. It is generated by `src/pages/resume.json.ts` from the same import, never maintained separately. It MUST be served with `Content-Type: application/json`.

**RES-06** `/resume/` MUST render, in this order: name, label and location; one-paragraph summary; a *Download PDF* link (visible without scrolling at 390 px and 1280 px widths); skills grouped as in the source; experience newest first with company, role, dates and highlights; education if present; the three profile links. All of it is real HTML text — no canvas, no SVG text, no images of text — so applicant-tracking systems and screen readers read it as written.

**RES-07** Computed facts rendered on the page: total years of experience (from the earliest `work[].startDate` to today, rounded down, as *9+ years*), per-skill years where a skill's `keywords` match the stack listed in `work[]` entries (optional at MVP; MUST NOT show a number that is not derived), and *present* for an open `endDate`. The build date is the reference "today", so the number updates on every deploy.

**RES-08** `/resume.pdf` is produced in CI (`05-pipelines.md` PIPE-08) by loading the built `/resume/` page in headless Chromium with the print media type and `page.pdf({ format: 'Letter', printBackground: true, preferCSSPageSize: true })`. The PDF MUST have selectable, searchable text with fonts embedded; MUST be ≤ 2 pages (the pipeline fails otherwise); SHOULD be ≤ 300 KB. It is uploaded to the site bucket beside the HTML with `Cache-Control: public, max-age=0, must-revalidate`.

**RES-09** The print stylesheet (`@media print` in the résumé page's styles) MUST: hide the site header, footer, theme toggle and any island; use the light "paper" tokens regardless of the viewer's theme; set `@page { size: Letter; margin: 0.6in }`; render link URLs for profile links as visible text; avoid page breaks inside a single `work[]` entry (`break-inside: avoid`); use the same type scale as the screen version reduced by one step.

**RES-10** JSON-LD `Person` (`07-discoverability.md` DISC-06) MUST be generated from `basics`: `name`, `jobTitle` (= `label`), `email`, `url`, `sameAs` (= `profiles[].url`), `worksFor` (= newest `work[].name`), `address.addressLocality`/`addressRegion` when `basics.location` is set, `knowsAbout` (= flattened `skills[].keywords`).

**RES-11** A post-build check (`scripts/check-resume.mjs`, run as part of `pnpm build`) MUST verify that every site-relative `evidence` URL exists in `dist/`, that `dist/resume.json` parses and contains no object-form highlights, and that no `TODO(michael)` string is present in `dist/resume/index.html`.

**RES-12** The résumé page is a normal content page for performance purposes at MVP: 0 KB client JavaScript other than the global theme toggle (`03-frontend.md` FE-30). The interactive parts below ship as islands later and are governed by the 40 KB budget.

### Phase 2 — role timeline

**RES-20** An SVG timeline drawn at build time (an Astro component, no client JavaScript) MUST appear above the experience section and in miniature on the home page: one row per `work[]` entry, a bar from `startDate` to `endDate` or today, the company name at left, years as axis ticks, the current role in the accent colour. Gaps between roles render as gaps; nothing is smoothed. Hover reveals the role's stack via a `<title>` element (native tooltip), which also serves screen readers. Reduced-motion: the component has no motion.

### Phase 3 — lenses and evidence

**RES-30** Three toggle buttons, *Leadership*, *Architecture*, *Consulting*, highlight highlights tagged with that lens and dim (never hide or reorder) the others. Implemented as a small island (vanilla `<script>` or Preact, ≤ 8 KB gzipped). Keyboard operable (buttons, `aria-pressed`), state in the URL hash (`#lens=leadership`) so a lens can be linked to, and no state persisted. Default: no lens. The print view ignores lenses.

**RES-31** Highlights carrying `evidence` render the number or phrase that the evidence supports as a link to it, with `rel="me"` omitted and a small arrow glyph. Ship this once at least one evidence URL exists (the Native AOT post, Phase 2).

**RES-32** Tailored PDF (pick a lens, download a one-page version) is explicitly deferred; it needs its own ADR and is not part of Phase 3.

## Seed data

`src/data/resume.json` in this repository is the seed, transcribed from Michael's résumé of 2026-10-24 with the phone number omitted and the summary carried verbatim. Lens tags were assigned by the author of this document and are a proposal for Michael to edit. Dates are month precision; where the résumé gave only month and year, the first of the month is used.

## Acceptance criteria

- [ ] `pnpm build` fails if `resume.json` has a highlight with an unknown lens, an `endDate` before `startDate`, or a dangling `evidence` URL.
- [ ] `/resume/` at 390 px shows name, summary and the PDF link without scrolling.
- [ ] `dist/resume.json` validates against the official JSON Resume schema (use the `resume-schema` package in `tests/resume.test.ts`).
- [ ] `resume.pdf` is ≤ 2 pages, has selectable text (`pdftotext` returns the name), embeds fonts (`pdffonts` shows no non-embedded fonts).
- [ ] The years-of-experience figure on the page equals `floor(today − 2017-05-01)` in years.
- [ ] Printing `/resume/` from a browser and the CI PDF are visually the same document.
